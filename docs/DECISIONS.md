# 実装上の判断記録（DECISIONS）

仕様書（[SPEC.md](SPEC.md)）の曖昧な点の解釈、仕様から外れた判断、技術選定の変更を記録する。
各項目に「判断」と「理由」を書く。仕様書の節番号を併記する。

## ゲームロジック

### D-01 「命中したヒントの遠さ点」は、命中が出た射で公開したヒントの点（2.5）

- 判断：第k射で命中したら、出題順k番目のヒントの遠さ点を使う。狙撃手が「どのヒントで分かったか」を申告する方式にはしない。
- 理由：1射で1つずつヒントを公開する進行（2.4）と自然に対応し、観測手の入力も増えないため。

### D-02 「元に戻す」は直前の1操作だけ。命中でラウンドが終わった直後も取り消せる（3.7）

- 判断：取り消せるのは直前の1操作のみで、続けて遡ることはできない。脱落を伴わない命中でラウンドが終わった場合は、ラウンド結果画面に進む前なら取り消して射撃中に戻せる。最後のパス・誤射で逃げ切りになった場合も同じ。結果画面に進んだら確定する。脱落を伴う操作は取り消せない（仕様どおり）。
- 理由：「命中」は誤タップを確認ダイアログで防いでいるが、確認後の誤りにも備えるため。

### D-03 使用済みのお題の範囲（2.2）

- 判断：ランダム抽選から外すのは、(a) 出題された単語、(b) 引き直しで捨てた単語、(c) 任意出題のお題のうち表記が辞書の word と完全に一致するもの（D-06 の正規化後）。
- 理由：(b) は標的が一度見ているため。(c) は同じお題の重複を避けるため。表記ゆれまでは追わない。

### D-04 延長戦・サドンデスでも狙撃手の回答順は観測手が登録する（2.4, 2.7）

- 判断：本戦と同じく、ラウンドごとに観測手が回答順を登録する。狙撃手が1人のときはこの画面を省略する。
- 理由：仕様書はサドンデスの標的順についてしか書いておらず、回答順の扱いを本戦と揃えるため。

### D-05 延長戦・サドンデスのラウンド番号の表示（3.4）

- 判断：「延長戦 第Nラウンド」「サドンデス 第Nラウンド」と番号を1から数え直して表示する。内部の輪番は通しのラウンド番号で続ける。
- 理由：周回上限を超えた周番号を表示すると分かりにくいため。

### D-06 ヒントの重複・お題との同一判定の正規化（2.3）

- 判断：前後の空白を除き、Unicode NFKC 正規化をしたうえで完全一致なら同一とみなす。ひらがなとカタカナ、大文字と小文字（NFKC で揃わないもの）は区別する。
- 理由：全角と半角、空白だけの違いは明らかに同じ文字列なので弾く。それ以上の同一視は観測手の判断に任せる。

## 画面・保存

### D-07 終了したゲームの保存データ（3.2, 3.10）

- 判断：結果発表のあとにアプリを開き直した場合、トップに「前回の結果を見る」を出す。保存データは仕様どおり次のゲームを始めた時点で削除する。起動時の「続きから／新規」ダイアログは、未完了のゲームがあるときだけ出す。
- 理由：終了したゲームを「続きから」と呼ぶのは不自然なため。

### D-08 HP推移グラフの横軸はラウンド単位（3.10）

- 判断：開始時点と各ラウンド終了時点のHPを打つ。脱落したラウンドは脱落した時点の値を使う。
- 理由：射ごとに打つと点が多すぎて、スマホの縦画面で読めないため。

## CONFIG

### D-09 上限が書かれていない項目の上限は 999（4章）

- 判断：上限HP（「開始HP以上」とだけある）、回数点、遠さ点の各値の上限を 999 とする。
- 理由：入力の範囲チェック（3.12）に上限が必要なため。開始HPの上限に揃えた。

## 技術

### D-10 lint は ESLint ではなく oxlint（6章、計画からの変更）

- 判断：lint に oxlint を使う。整形は Prettier。
- 理由：create-vite の react-ts テンプレートが TypeScript 7 と oxlint を標準にしている一方、typescript-eslint は TypeScript 6.1 未満にしか対応していない。ESLint のために TypeScript を下げるより、テンプレート標準に合わせた。型の厳密なチェックは `tsc`（strict）が担い、react-hooks のルールは oxlint の react プラグインで有効にする。

### D-11 Node.js は 26 LTS（計画からの変更）

- 判断：Node.js 26 LTS を使う（`package.json` の `engines` と `.nvmrc` に記載）。
- 理由：計画時に挙げた 22 は古い。導入時点の LTS に合わせた。

### D-12 GitHub リポジトリの作成と Vercel への接続はプロジェクトの持ち主が行う（6章）

- 判断：リポジトリ（https://github.com/Sabu-chan/MiND_SNiPER ）の作成と Vercel への接続は持ち主が行う。実装側は `vercel.json`（全パスを index.html に書き換え）を用意し、段階ごとのコミットを `main` に push する。
- 理由：アカウントの権限設定や外部サービスとの連携は持ち主が管理するため。

## 段階2（ゲームロジック）で決めたこと

### D-13 最終順位の付け方（3.10）

- 判断：勝者（引き分けなら同点者全員）を1位とする。以降は、後まで勝ち残っていた人ほど上位とし、同じ判定で勝ち残りから外れた人どうしは、外れた時点のHPの多い順に並べる（同点は同順位）。
  - 例：本戦で脱落者が出て A・B が同点、C が3位相当 → サドンデスで A が勝てば、1位 A、2位 B、3位 C、4位 脱落者。
- 理由：仕様書は「順位と最終HPを発表」とだけ書いている。最終HPだけで並べると、サドンデスでHPを削り合った人が、サドンデスに出られなかった人より下になることがあり、勝敗の流れと合わない。表示する最終HPは実際の値のまま。

### D-14 出題順のシャッフルは承認の操作で行う（2.3-7, 3.6-5）

- 判断：仕様書では「射撃開始」でシャッフルするとしているが、内部では観測手が「承認」した時点でシャッフル結果を決めて保存する。出題順は射撃が始まるまでどの画面にも表示しないので、遊ぶ側から見た違いはない。
- 理由：狙撃手が1人で回答順の登録画面を省略する場合も、同じ処理で済むため。乱数の結果はアクションに含めて渡し、ゲーム進行のリデューサーを純粋関数に保っている。

### D-15 続きから再開するときの受け渡し画面（3.2）

- 判断：出題（標的）・承認（観測手）は、受け渡し画面から長押しで再開する。回答順の登録・射撃・サドンデスの標的順の登録（いずれも観測手が操作し、秘密情報を表示しない）は、観測手への受け渡し画面から通常のタップで再開する。ラウンド開始・ラウンド結果・告知・結果発表は全員に見せる画面なので、そのまま再開する。
- 理由：仕様書の「必ずその場面の受け渡し画面から再開する」に従いつつ、長押しは秘密情報を開くときだけにする（3.1）。

### D-16 辞書の一覧ファイル（index.json）の形式（5.1）

- 判断：`{ "version": 1, "dictionaries": ["<ファイル名>.json", ...] }` とする。ファイル名は英数字・`_`・`.`・`-` のみで、パスを含むもの、`index.json` 自身、重複は除外して警告する。辞書をまたいで単語を区別するため、内部では `<ファイル名>#<id>` をキーにする。同じ id のカテゴリが複数の辞書にあれば1つにまとめる（表示名は先に読み込んだもの）。
- 理由：仕様書は「index.json に辞書ファイル名の一覧を置く」とだけ書いている。形式にもバージョンを持たせ、将来変更できるようにした。

## 段階3（画面）で決めたこと

### D-17 プレイヤー登録とゲーム画面にも URL を割り当てる（6章）

- 判断：トップ（/）・ルール説明（/rules）・CONFIG（/config）に加えて、プレイヤー登録（/new）とゲーム画面（/play）をルーティングする。ゲーム内の場面（受け渡し・出題・承認・射撃など）はすべて /play の中で状態機械によって切り替え、URL には一切出さない。
- 理由：ゲーム中にルール説明や CONFIG を開いて「戻る」でゲームに戻れるようにするため。URL に秘密情報を含めないという仕様の目的は保たれる。

### D-18 出題画面の入力途中の内容は保存しない（3.5, 5.2）

- 判断：標的が入力中のお題・ヒントは「確定」するまで画面の中だけで持ち、ゲーム状態（保存の対象）には入れない。ゲーム中にルール説明などを開いて戻った場合や、再読み込みした場合は入力し直しになる。ランダム出題の抽選結果は、引き直し回数を守るためゲーム状態に保存する。
- 理由：ゲーム状態の保存は「操作のたび」（5.2）としており、文字入力は操作に含めない。入力途中の秘密情報を保存データに残さないためでもある。

### D-19 ランダム出題を選ぶとすぐに1回目を抽選する（3.5）

- 判断：出題方式で「ランダム出題」を選んだ時点で1回目の抽選を行い、結果を表示する。1回目は引き直し回数に数えない。一度抽選した単語は、任意出題に切り替えても使用済みとして扱う（D-03）。
- 理由：抽選のためだけの操作を1つ減らすため。

### D-20 ラウンド結果・告知の「次へ」ボタンは行き先を書かない（3.8, 7章）

- 判断：ラウンド結果画面のボタンは、次が通常のラウンド・延長戦・終了のいずれでも「次へ」と表示する。
- 理由：ボタンの文言で「次で終わる（＝誰かが周回上限で単独1位）」などが推測できないようにするため。

### D-21 長押しボタンはキーボードでも操作できる（3.1）

- 判断：Enter または Space の押し続けでも発動する。右クリックや長押しのコンテキストメニューは無効にする。
- 理由：アクセシビリティのため。発動条件（押し続けること）は指と同じ。

### D-22 デバッグ表示は既定で閉じる（6章）

- 判断：開発時のデバッグ表示（全員のHPと遠さ点）は画面下部の折りたたみに置き、開いたときだけ中身を描画する。本番ビルドでは import.meta.env.DEV によって読み込み自体を行わない（ビルド結果に含まれないことを確認済み）。
- 理由：開発中にも秘匿が守られているかを目で確かめられるようにするため。

### D-23 サンプル辞書（5.1）

- 判断：動作確認用に public/dictionaries/sample.ja.json を置く（都道府県・国名・山・動物・食べ物、各3〜4件）。本番辞書で置き換える前提。

## 段階4（CONFIG・ルール説明・保存・PWA・グラフ）で決めたこと

### D-24 表示言語は CONFIG の一部として保存する（4章, 5.2）

- 判断：保存するもの（ゲーム状態・CONFIG・前回のプレイヤー名・表示言語）のうち、表示言語は CONFIG の項目として `mind-sniper:config` に一緒に保存する。キーは `mind-sniper:game`・`mind-sniper:config`・`mind-sniper:player-names` の3つ。
- 理由：第4章で表示言語は CONFIG の項目になっており、別のキーに分けると二重管理になるため。表示言語の変更は保存した時点で画面に反映する（ゲームに固定する値とは別に、画面の言語はすぐ切り替える）。

### D-25 保存データの読み込み（5.2）

- 判断：ゲーム状態は schemaVersion が一致し、形の大枠と固定した CONFIG が正しいものだけを読む。CONFIG は保存後に増えた項目を初期値で補ってから範囲チェックし、通らなければ破棄して初期値に戻す。どちらも破棄したときはトップに「読み込めなかったため削除しました／初期値に戻しました」と表示する。
- 理由：「読めない古いデータは破棄し、その旨を表示する」の具体化。項目の追加だけで設定が消えないようにした。

### D-26 アプリ内の「続きから」でも受け渡し画面から再開する（3.2）

- 判断：起動時の再開だけでなく、ゲーム中に「中断してトップへ」から「続きから」で戻る場合も、出題・承認などは受け渡し画面から再開する（D-15 と同じ規則）。
- 理由：中断している間に端末が別の人の手に渡っている可能性があるため。

### D-27 PWA の設定（6章）

- 判断：manifest の display は fullscreen（対応しない環境では standalone）、向きは縦。Service Worker は新しい版を自動で取り込む（autoUpdate）。辞書（public/dictionaries/*.json）を含む全ファイルを事前キャッシュする。アイコンは public/icon.svg から @vite-pwa/assets-generator で生成した PNG。
- 理由：オフラインでも辞書を使えること、ホーム画面から全画面で開けることが要件のため。辞書を足したときは index.json の内容が変わるので、次のデプロイでキャッシュも更新される。
- 補足：npm audit が開発用の依存（vite-plugin-pwa が使う workbox-build 内の glob / minimatch）に中程度の脆弱性を報告する。ビルド時にだけ使い、配信するアプリには含まれない。修正案は vite-plugin-pwa を1系に戻す破壊的変更なので、上流の更新を待つ。

### D-28 HP推移グラフの作り（3.10）

- 判断：自前の SVG 折れ線。系列の色は検証済みの8色パレットの先頭から席順で固定に割り当てる（最大6人）。ライト・ダークそれぞれの色をパレット検証スクリプトで確認した（全項目合格。ライトでは3色が背景とのコントラスト3:1未満のため、凡例と表での表示を必ず付ける）。凡例は常に表示し、なぞる・タップする・矢印キーでそのラウンドの全員のHPを表示する。同じ値を表でも見られる。
- 理由：外部のグラフライブラリを入れずに、オフラインでも軽く動かすため。色だけに頼らずに読めるようにするため。

## 公開後の変更

### D-29 画面の用語：「周」→「ラウンド」、「ラウンド」→「ゲーム」、試合全体→「試合」（1章、仕様からの変更）

- 判断：画面の文言だけを次のように変える（2026-11-09、持ち主の指示）。仕様書・コード・テストの説明文は仕様書の用語のまま。
  - 全員が1回ずつ標的を務めるまとまり（仕様書の「周」）→「ラウンド」。見出しは「第1ラウンド（全3ラウンド） 第2ゲーム」、CONFIG は「ラウンド上限（1〜10ラウンド）」。
  - 1人の標的による1出題（仕様書の「ラウンド」）→「ゲーム」。「ゲーム開始」「ゲーム結果」「全ゲームの記録」、延長戦・サドンデスは「延長戦 第1ゲーム」、グラフの横軸は G1, G2, …
  - 試合全体の意味の「ゲーム」は、上の「ゲーム」と紛らわしくなる箇所（脱落の告知「脱落者が出ました。試合終了」、ルール説明の勝敗、中断の確認、CONFIG の「変更は次の試合から反映」）を「試合」にする。トップの「新規ゲーム」「保存中のゲームは削除されます」などは変えない。
- 理由：持ち主の指示。「ゲーム」が1出題と試合全体の両方を指すと「ゲーム終了」の意味が取れなくなるため、試合全体のほうを「試合」と書き分けた。
